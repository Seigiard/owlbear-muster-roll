# Adversary review: AD-20 to AD-25 (v2 preset builder)

Verdict: **revise** (small, targeted AD edits; the structure is sound). Six holes let two compliant builders produce incompatible parts.

## Findings

1. **AD-21: the document's shape is not fixed, so store and forms/tree can disagree.** "A mirror of the preset with uids" does not say where the uid sits (`{uid, ...cell}` vs `{uid, value}` wrapper), whether cells keep `kind`-specific fields, nor how uids are stripped to a `Preset`. Builder A wraps nodes, builder B spreads the uid in; the tree (keys = uids), the preview (index path to uid) and `presetProblems` (index path) then use different accessors. Fix: add to AD-21 "The document type is `Preset` with an added `uid: string` on each template, section, row and cell, one `toPreset(doc)` and one `fromPreset(preset)` in `src/builder` are the only conversions, and uids are never part of any equality or coalesce key."

2. **AD-21: coalesce key and selection are unowned.** "Same coalesce key as the one before" does not say what a key contains (field + uid?), whether it breaks on selection change, on blur, or on undo, nor whether selection and the opened-file origin are inside the undone document. Two builders will make undo restore different selections, or merge a rename of two different fields into one step. Also "file open" is a document change, so undo after open returns to the old draft, but the origin/name are outside the document. Fix: add "A coalesce key is `{kind, uid, property}`; any undo, redo, other-key edit or selection change ends the run; selection, origin and name are store state outside the undo stack, and opening a file or starting blank clears both stacks."

3. **AD-24 / CAP-25: row identity and repeat-section identity are the first field id, and no AD covers it.** In `core/preset` a plain row's `row:` record name is `firstFieldId(row)` and a repeat section's `rep:` name is its first field's id (`repeatSectionId`). So reordering cells/rows (AD-25 moves), deleting the first field, or changing a field type change which values survive an upload, not only an id rename. CAP-25's "changed id warns" is therefore under-specified: one builder warns only on rename, another also on moves/deletes; a repeat section whose first field is moved out becomes `bad-repeat`. The preview's "one empty `rep:` record per repeat section" also needs this key. Fix: add to AD-24 "The warning that stored values will be erased is computed by one core function that compares the set of field ids, row ids (`firstFieldId`) and repeat section ids (`repeatSectionId`) of the opened-file preset with the current one, so a rename, move or delete all raise it."

4. **AD-24: "label" and "rename also affects `nameField`/other refs" are undefined.** The field cell has no label; the label is the preceding `text` cell in the row (`cellLabel` in `preset-cell.tsx`). `field-id-suggest` takes "a label" but the AD does not say it is that text cell, what happens with no preceding text, or when the id is made (on creation only, per the spec, but the label may be typed after). Also a rename that makes an id collide in its scope: AD says the id is checked, but not whether the rename is refused or accepted-as-problem (AD-25 accepts invalid moves; AD-22 allows invalid states). Another gap: a move across scopes (AD-25) changes how existing formulas resolve, and nothing says whether `formula-rename` or a "formula now unresolved" signal runs. Fix: add to AD-24 "The label is the text of the nearest `text` cell before the field in its row, an empty one gives the id `field`; a rename to a taken or invalid id is accepted and shown as a problem, never refused; a move never rewrites a formula."

5. **AD-23: the preview supplies no contract for `editing`, `rolling`, `pending` and `blockTools`, and AD-20's import ban conflicts with the sheet module.** `SheetBody` requires `editing`, `rolling` (typed with `ProjectionStore`/`ReplicaClient` in `dice-button.tsx`), and `pending`. Builder A passes `editing: null` (read-only, no placeholder-fill), builder B passes a local fake store, so one preview accepts typing and the other does not; dice buttons either roll through a fake or are dead. Moreover AD-20 forbids importing the replica client/projection store while the sheet module imports them (even as types), so "only the sheet modules" cannot both hold. Fix: add to AD-23 "The preview passes `editing: null`, `pending: null`, `blockTools: null` and a `rolling` that does nothing, built in one `src/builder` function, and sheet modules import the replica client and projection store as types only; AD-20 bans the values, not the types."

6. **AD-22: `presetProblems` has no problem identity or target granularity.** "Every rule failure with its index path" does not say how to place cross-item failures: `duplicate-id` (which of the two cells?), `duplicate-template`, `bad-name-field` (template vs the field), `bad-repeat` (section, since there is no field), `duplicate-section`, and the builder-only `no templates` and `bad-window` (no template path at all). Builders will mark different items, so the counter's "first error" and the tree/preview marks disagree. "Order parsePresetFile checks" also keeps zod refine errors (`tokens` without `repeat`, `players` on a set) out of scope, because those fail at `invalid-structure` before the rules. Fix: add to AD-22 "Each problem carries one path, the later occurrence for a duplicate, the template for `bad-name-field` and `duplicate-template`, the section for `bad-repeat` and `duplicate-section`, and none for window and empty-templates; the structure schema is applied to the document so that no document is in a state the schema cannot hold (`tokens` is cleared when `repeat` is cleared)."

7. **AD-25: "a drop that breaks a rule is accepted" collides with the structure schema, and the drag types do not cover cross-kind needs.** Some drops are legal moves but produce a state `parsePresetFile` reports as `invalid-structure` (not a rule problem): a row under a section whose `columns` is smaller, or the last row removed. More important, CAP-23 needs creating and deleting nodes, which AD-25 does not cover (add buttons, default content, delete confirm). The rule "each is one store edit" applies only to moves. Fix: add to AD-25 "Add, delete, duplicate and move are all one `apply` of a named edit in `src/builder/edits`; each new node gets defaults that pass the structure schema."

8. **AD-20 / CAP-21: the Settings button and the cross-page format are open.** The spec itself lists as open that the iframe may not open a new tab; AD-20 decides on `/builder.html` in a new tab without a fallback (a plain link vs `window.open` vs the SDK's `modal`), and the download file name (spec: name and time) and the name's source are not in an AD. Fix: add to AD-20 "The Settings control is a real `<a href="/builder.html" target="_blank" rel="noopener">`; if the SDK blocks it, the task stops and escalates instead of choosing another route."

9. **CAP-26 vs AD-21: a draft that is valid structure but opened with an origin that is stale.** The origin (opened file preset) is saved in the draft, but two builder tabs share the one `localStorage` key and each writes the whole draft after every change, so the last writer wins silently. Spec says one draft; no AD says what a second tab does. Fix: add to AD-21 "A second open builder tab reads the draft once and does not subscribe; the draft key carries a write time, and a tab whose loaded time is older than the stored one shows a banner instead of writing."

## CAP success criteria left open

- CAP-22 "a form edit redraws the preview at once": no AD says whether the preview reads the store directly or a debounced copy (coalesced typing vs a deferred derived record). Add one line in AD-23: the preview subscribes to the document store with no debounce.
- CAP-27 "each edit kind can be undone": there is no list of edit kinds (move, add, delete, rename-with-formula-rewrite). The rename must be a single step that includes the formula rewrites (AD-24 does not say), otherwise undo restores the id but not the formulas.
- CAP-28 "problem counter jumps to the first": "first" is by `presetProblems` order, which is check order, not tree order; one builder will sort by tree position. Say in AD-22 that first means first in tree order of the path.
